# MySQL EXPLAIN 与索引排查

## 背景与目标

在日志列表与统计查询中，即使页面只展示少量记录，数据库也可能需要先筛选大量明细、关联配置、计算总数并排序。一次排查中的传统格式 `EXPLAIN` 显示：大表以 `ALL` 访问且 `key` 为空；关联表出现 `eq_ref`；列表查询出现临时表、额外排序和相关子查询。这些迹象用于提出假设，不能单凭它们确认性能瓶颈。

以下以 MySQL 8.0 的传统 `EXPLAIN` 为背景；示例表名、数字和 SQL 均为虚构教学素材，不对应生产表。实际执行计划与效果依赖版本、数据分布和查询条件。参考 [[SQL 条件判断与聚合统计]] 了解聚合口径。

## 先区分三种时间和数量

- 普通 `EXPLAIN SELECT ...` 展示优化器的**预估计划**；平台展示的这次命令耗时不是原始查询的执行耗时。
- `rows` 是预估读取行数；`filtered` 是预估经过该表条件后保留的百分比。两者相乘可粗略估计该步输出行数，不等于整条 SQL 的实际扫描量或结果总数；连接时还需考虑外层循环次数。
- 实际查询耗时需要单独执行查询测量。`EXPLAIN ANALYZE` 会实际执行查询并报告运行信息，适用语句与能力依 MySQL 版本而异；生产使用前评估负载，不把它当作普通 `EXPLAIN`。

## 传统 EXPLAIN 字段怎么读

| 字段 | 含义和阅读方法 |
| --- | --- |
| `id` | 查询块的标识；辅助识别主查询和子查询，不能单凭数字推断完整的实际执行顺序。 |
| `select_type` | 查询块类型：`SIMPLE` 表示简单查询；`PRIMARY` 表示最外层查询；`DEPENDENT SUBQUERY` 表示依赖外层值的子查询。 |
| `table` | 当前步骤涉及的表或别名；`<derivedN>` 等可能代表派生结果。 |
| `partitions` | 预计访问的分区；非分区表通常为 `NULL`。是否能裁剪分区要结合真实分区定义和条件判断。 |
| `type` | 访问方式。`ALL` 为全表扫描，`index` 为索引扫描，`range` 为索引范围访问，`ref` 为非唯一键或索引前缀等值访问，`eq_ref` 通常是对前面每个行组合按主键或非空唯一键最多匹配一行；还可能出现 `const` 等。它是线索，不是独立的快慢排名。 |
| `possible_keys` | 优化器认为可能使用的索引，不代表最终采用；`NULL` 也不应单独当作完整诊断结论。 |
| `key` | 计划选中的索引；`NULL` 表示该表访问未选择索引。 |
| `key_len` | 计划使用的索引键长度，单位为字节；受类型、字符集、可空性等影响，不能简单等同字段数量或索引好坏。 |
| `ref` | 与所选索引比较的常量或列；`func` 表示使用计算结果，可结合 `SHOW WARNINGS` 和具体 SQL 分析，不能仅凭该值判断是否发生全表扫描。 |
| `rows` | 优化器估计需要检查的行数，实际值可能不同。 |
| `filtered` | 估计经过该表条件后保留的行百分比，不是索引命中率。 |
| `Extra` | 附加执行信息，应与其他列一起分析。 |

### 常见 Extra

- `Using where`：还有条件用于过滤；不等于没有使用索引。
- `Using index`：通常表示所需列可从索引获取，即覆盖索引；是否需要额外访问行以及特殊情况要结合执行计划判断。
- `Using temporary`：使用临时表，可能涉及分组或排序等；不代表一定写入磁盘，也不单独证明慢。
- `Using filesort`：执行额外排序；名称不意味着一定产生磁盘文件，也不等于一定有问题。排序的数据量和代价需要实测。
- `Using join buffer (hash join)`：使用连接缓冲及哈希连接；结合驱动表、访问行数及 MySQL 版本分析，不直接判为异常。

| 假设观察 | 可以确认 | 下一步要验证 |
| --- | --- | --- |
| 明细表 `type=ALL`、`key=NULL`、`rows` 数值较大 | 优化器计划扫描表，`rows` 是估计值 | 确认时间条件、实际索引、数据分布和真正耗时 |
| 关联表 `type=eq_ref`、`key` 为唯一索引、`ref=func` | 该关联访问计划使用唯一键，比较值包含计算结果 | 对列使用函数是否限制另一侧索引利用；查看完整 SQL 和计划 |
| 列表查询出现 `Using temporary; Using filesort` | 计划涉及临时处理和额外排序 | 评估排序前候选量、排序条件及实测成本 |
| `DEPENDENT SUBQUERY` 行使用组合索引，但有 `Using filesort` | 子查询依赖外层值，计划中使用了索引且还需排序 | 衡量调用次数与排序成本；不能认为每个子查询都必然逐行重算 |

同一张计划中同时出现全表扫描、排序和子查询时，应分别测量并优先处理证据最强的环节，而不是只凭一个字段断言根因。

## 索引和 SQL 优化思路

1. **核对时间条件与索引列**：业务发生时间和写入时间可能不同。查询按发生时间筛选时，写入时间的单列索引不能直接当作等价替代；不能为了命中索引随意附加另一时间范围，否则延迟数据可能漏查。
2. **评估时间范围索引**：对频繁用于范围筛选的列考虑单列索引，比较 `possible_keys`、`key`、`rows` 和实际耗时。范围命中比例高时优化器仍可能选择扫描；索引也增加写入与存储成本。
3. **谨慎处理列上的函数**：例如 `TRIM(code)` 与 `code = ?` 语义可能不同。普通列索引对表达式不一定能直接用于查找；可在验证兼容性与版本后评估规范化字段或函数索引，不要直接移除函数而忽略历史数据。
4. **计数与列表分别检查**：精确总数与分页查询是不同工作。只用于展示的关联可能不参与计数，但优化器可能已消除部分关联，且筛选依赖的关联不能省略。
5. **排序和大字段**：跨表排序、深页偏移及大文本读取可能提高成本。可评估先在保留完整筛选和排序语义的前提下定位当前页，再补充详情；筛选条件依赖关联数据时，不能把相关过滤简单移到分页之后。
6. **重复聚合**：若一次请求对同一范围重复汇总，可评估合并或限定后续查询范围；如先按总调用量排序，就必须在确定分页前得到正确排序所需的总量，并保留零调用、空值及失败分类规则。
7. **不要把组合主键当作任意列的独立索引**：例如 `(id, created_at)` 按最左前缀支持查找，不应假定等价于仅对 `created_at` 的索引；仍需考虑优化器的其他访问策略并验证计划。
8. **替换索引前查用途**：历史汇总、清理、报表及外部同步可能使用拟删除的索引。先核对线上工作负载，再评估替换、回退及 DDL 对写入的影响。

## 分页排序内存不足与两阶段查询

### 现象和诊断

MySQL 返回错误 1038（`Out of sort memory`）表示执行过程中的排序未能在现有条件下完成，但单凭错误或 `Using filesort` 无法判断是哪一个排序节点、是否排序了所有候选行，或大文本是否实际进入排序元组。`LIMIT` 也不保证只读取或处理页面大小的候选数据。普通 `EXPLAIN` 是预估计划；检查实际查询耗时、完整 SQL、范围条件、索引及排序，再按需要评估排序模式和内存使用。

跨表的 `ORDER BY CASE ...` 可能无法由单表索引直接提供完整顺序。时间范围索引有助于定位候选行，但不意味着满足另一组排序；排序顺序涉及业务规则时不能为了消除 filesort 随意改成按时间或主键排序。

### 可选方案：先定位主键，再批量取明细

第一步保留所有筛选、关联和排序规则，只查询当前页的完整主键；第二步用这些主键一次性回查所需字段，在应用层按第一步的顺序组装。请求和响应等大字段不在主分页查询的投影中，通常可以减少排序阶段携带的数据；实际排序元组和收益仍由 MySQL 计划决定，必须实测。

- 每个影响页面成员的条件都必须在第一步生效；依赖关联表或最新状态的条件，也不能放到分页之后。
- 使用完整主键或唯一键匹配；例如 `PRIMARY KEY (id, created_at)` 支持两个字段一起精确查找，不需要为了该回查单独创建 `created_at` 索引。但它不等同于以 `created_at` 为首列的索引，不能直接替代其他按时间列筛选的工作负载。
- 第二次 SQL 返回顺序不保证与第一步一致，应按完整键恢复原顺序；空主键页直接返回，并保留原有总数。批量大小需有上限，避免逐条回查形成 N+1。
- 非事务的两步查询可能看到不同快照：某行在筛选后状态变化，展示值可能与筛选条件暂时不一致；记录被清理可能形成短页。若要求同一请求一致性，应评估短只读事务、隔离级别及其代价，而不是简单地在第二步重复过滤后假定语义不变。
- 额外的一次数据库往返、深页 `OFFSET`、计数查询及跨表排序仍可能是瓶颈；不能承诺该方案一定消除 filesort、1038 或深页成本。加大 `sort_buffer_size` 不是首选，且应评估每连接内存与并发影响。

### 对照验证

使用相同的固定时间范围、筛选、排序、页码和页大小，分别记录原列表查询、主键分页、明细回查及计数的实际结果和耗时；检查每一步的 `EXPLAIN`，明细回查关注 `key=PRIMARY` 或其他唯一键。确认结果的完整键集合与顺序一致，并测试空页、同 ID 不同复合键、筛选组合和并发状态变化。旧查询报错时无法计算准确加速倍数；新两步耗时相加只是数据库侧近似值，不等于包含网络与应用处理的页面耗时。

实践边界：在一次 MySQL 兼容环境的实际测试中，原列表查询触发 1038；拆分后的主键分页与明细回查分别成功，主键分页计划仍有临时表和 filesort，明细回查计划使用主键。具体排序模式、错误触发的精确内部机制和部署后的页面效果没有被该实验单独证明。服务器精确版本未核实，以上机制应结合目标版本复验。

## 实验与结果记录

1. 核对数据库版本、实际表结构、索引、查询参数和上线代码版本；先保存变更前计划及实际耗时。
2. 选择已结束的固定时间段，在前后尽量相近的负载、缓存与权限条件下，分别测量计数和列表 SQL，重复多次记录每次耗时。
3. 索引变更后使用完全相同的 SQL 和参数复测；比较 `key`、`type`、估计 `rows`、`Extra` 和实际耗时，并检查写入影响。
4. 在授权范围内，`IGNORE INDEX` 可用于只读查询的对照探索，但它影响优化器选择，不能证明实际删除索引后的全部工作负载表现。
5. 记录数据范围、结果数量和业务口径一致性；计划变化不等于性能必然改善，也不能把尚未取得的索引后结果写成成功。
