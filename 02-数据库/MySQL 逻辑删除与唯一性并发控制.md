# MySQL 逻辑删除与唯一性并发控制

## 现象与原因

逻辑删除通常保留原行，并将删除标志置为已删除。普通唯一索引仍会检查这行，因此同一业务值重新插入可能发生唯一键冲突；应用查询若没有排除已删除行，也会先报重复。数据库约束和应用查重是两道独立检查，变更时需要一起评估。

## 唯一性范围

先明确哪些字段在什么范围内唯一，例如“同一租户下名称唯一”“标识全局唯一”。只有有效记录参与查重时，查询需要显式过滤删除状态；更新时排除当前记录。禁用和删除是不同状态，是否允许禁用记录复用值由业务规则决定。

## 方案和权衡

- **数据库生成列与唯一索引**：MySQL 中可让生成列对有效行返回固定值，对已删除行返回 `NULL`，并将其加入唯一索引；MySQL 唯一索引允许多个含 `NULL` 的键值。这样可保留数据库并发兜底，也允许多条历史删除记录。实际生成列表达式、索引长度、字符集、版本、现存重复值及 DDL 风险应在目标库验证。简单地把布尔删除标志直接加入唯一键，只能容纳有限种删除状态，不能支持同值反复删除后保留多条历史。
- **业务层查重与共享锁**：当数据库不再用唯一索引约束这些字段时，仅有“先查询，再写入”不能防止并发重复。所有实例及所有写入口必须遵守同一互斥协议，锁覆盖查重、写入及物理事务提交或回滚。数据库事务行锁可以作为候选；协调行的稳定性、全局唯一字段的跨范围竞争、锁顺序与超时都需设计。直接 SQL、导入程序或旧版本绕过协议，仍能写出重复数据。
- **Redis 租约锁**：固定 TTL 如果早于事务完成而过期，另一写入可能同时进入。续期、故障、进程暂停与锁失效后的栅栏措施均需单独设计，不能仅凭“锁有过期时间”声称严格唯一。

去除唯一约束与去除查询索引是两个选择：适当的普通索引可能仍有助于过滤和排序，但应结合实际查询、执行计划、写入成本与数据分布评估，参见 [[MySQL EXPLAIN 与索引排查]]。

## 事务和缓存细节

MySQL InnoDB 的 `REPEATABLE READ` 下，普通一致性读可能沿用事务早先建立的快照；加锁读用于读取当前可见状态。加入已有外层事务时，内层声明的隔离级别不一定改变外层事务。查重与锁定查询还应考虑 ORM 一级缓存和二级缓存，确保请求实际到达数据库。

事务提交前先删除缓存，可能让并发读重新缓存提交前的数据。可按实际一致性需求在提交后触发失效；数据库提交与外部缓存操作不天然具备原子性，失败后的可见性和补偿策略需要明确。较慢的远程调用应尽量放在取得数据库锁之前；即便把它移到方法中的事务开始之前，调用方已经持有外层事务时仍要考虑外层事务的生命周期。

## 验证边界

目标概念以 MySQL 8.0 / InnoDB、Spring 事务为背景。并发单元测试和数据库替身可以验证业务调用顺序与错误处理，但不能证明真实数据库的锁范围、索引行为、隔离级别和跨连接并发效果；应在获授权的隔离测试库中使用真实事务与多个连接验证。本笔记未在目标 MySQL 环境运行示例，也不记录任何实际业务表结构。
