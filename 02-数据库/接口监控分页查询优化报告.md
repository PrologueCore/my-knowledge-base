## 一、问题背景

生产环境接口监控模块查询日志时，选择 **2026 年 11 月 3 日、全部状态**，页面提示“调用记录加载失败”。

后端日志显示，分页列表 SQL 执行时发生 MySQL 异常：

```
Error code: 1038
Out of sort memory, consider increasing server sort buffer size
```

生产日志表 `t_api_log` 约有 **170 多万条记录**。本次测试条件下，总数查询返回 **79,830 条**。每页虽然只展示 10 条，但数据库仍需从满足条件的记录中确定排序后的前 10 条。

原 SQL 同时查询请求参数、响应参数、错误信息等 `TEXT` 字段，并按接口当前告警状态及日志主键排序。结合报错与执行计划，可以确认**排序阶段发生了内存不足**；不过，仅凭现有截图，还不能确认 MySQL 当时具体使用的排序数据结构及各字段占用的内存。

## 二、优化前 SQL

以本次复现条件为例：查询 11 月 3 日、全部调用状态、全部处理状态、第 1 页，每页 10 条。

```
SELECT
    CAST(l.id AS CHAR) AS id,
    l.server_name,
    l.api_code,
    p.id AS api_id,
    p.api_name,
    c.channel_name AS provider,
    c.category,
    l.trace_id,
    l.start_at,
    l.end_at,
    l.cost_ms,
    l.success,
    l.http_status_code,
    l.biz_status_code,
    l.req_url,
    l.req_param,
    l.resp_param,
    l.error_msg,
    l.create_time,
    h.handle_action AS handle_status,
    h.handler_name AS last_handler_name,
    h.handle_time AS last_handle_time
FROM t_api_log l
LEFT JOIN t_party_api p
    ON p.api_code = TRIM(l.api_code)
LEFT JOIN t_channel c
    ON c.id = p.channel_id
LEFT JOIN t_api_log_handle_record h
    ON h.id = (
        SELECT r.id
        FROM t_api_log_handle_record r
        WHERE r.api_log_id = l.id
          AND r.api_log_create_time = l.create_time
        ORDER BY r.handle_time DESC, r.id DESC
        LIMIT 1
    )
WHERE l.is_del = 0
  AND l.start_at >= 1793635200000
  AND l.start_at < 1793721600000
ORDER BY
    CASE WHEN p.status = 1 AND p.alarm_status = 1 THEN 0 ELSE 1 END ASC,
    l.id DESC,
    l.create_time DESC
LIMIT 10 OFFSET 0;
```

### 原查询的特点

1. **时间筛选使用 `start_at`。** 生产环境当前已存在 `idx_start_at`，此次 `EXPLAIN` 显示日志表使用该索引进行范围扫描。
    
2. **排序包含跨表计算。** 排序第一项根据接口表 `t_party_api` 的 `status`、`alarm_status` 计算告警优先级，随后按日志的 `id`、`create_time` 倒序。现有的 `start_at` 单列索引不能直接完成这组跨表排序。
    
3. **查询字段较宽。** 列表 SQL 直接读取 `req_url`、`req_param`、`resp_param`、`error_msg` 等文本字段，同时还关联最新处理记录。
    
4. **`LIMIT 10` 不代表只处理 10 条候选记录。** 数据库需要先根据筛选和排序规则确定哪 10 条属于当前页。具体扫描和排序方式由优化器决定。
    

本次原 SQL 执行时直接报 1038，因此没有可用于比较的成功执行耗时。

## 三、优化后 SQL

优化后的列表查询拆成两步：**先筛选并确定当前页主键，再根据主键批量回查完整明细**。总数查询单独执行，其逻辑本次未改动。

### 第一步：筛选、排序并查询当前页主键

```
SELECT
    l.id,
    l.create_time
FROM t_api_log l
LEFT JOIN t_party_api p
    ON p.api_code = TRIM(l.api_code)
LEFT JOIN t_channel c
    ON c.id = p.channel_id
WHERE l.is_del = 0
  AND l.start_at >= 1793635200000
  AND l.start_at < 1793721600000
ORDER BY
    CASE WHEN p.status = 1 AND p.alarm_status = 1 THEN 0 ELSE 1 END ASC,
    l.id DESC,
    l.create_time DESC
LIMIT 10 OFFSET 0;
```

这一步保留原来的筛选与排序规则，只返回完整复合主键 `id + create_time`。

上面的 SQL 对应“处理状态为全部”的场景。实际代码中，如果用户指定了处理状态，第一步仍会关联最新处理记录，确保**处理状态筛选发生在分页之前**。

### 第二步：根据当前页主键批量回查明细

以下是 SQL 结构示例，实际运行时由应用将第一步查出的主键作为绑定参数传入：

```
SELECT
    CAST(l.id AS CHAR) AS id,
    l.server_name,
    l.api_code,
    p.id AS api_id,
    p.api_name,
    c.channel_name AS provider,
    c.category,
    l.trace_id,
    l.start_at,
    l.end_at,
    l.cost_ms,
    l.success,
    l.http_status_code,
    l.biz_status_code,
    l.req_url,
    l.req_param,
    l.resp_param,
    l.error_msg,
    l.create_time,
    h.handle_action AS handle_status,
    h.handler_name AS last_handler_name,
    h.handle_time AS last_handle_time
FROM t_api_log l
LEFT JOIN t_party_api p
    ON p.api_code = TRIM(l.api_code)
LEFT JOIN t_channel c
    ON c.id = p.channel_id
LEFT JOIN t_api_log_handle_record h
    ON h.id = (
        SELECT r.id
        FROM t_api_log_handle_record r
        WHERE r.api_log_id = l.id
          AND r.api_log_create_time = l.create_time
        ORDER BY r.handle_time DESC, r.id DESC
        LIMIT 1
    )
WHERE
    (l.id = ? AND l.create_time = ?)
    OR (l.id = ? AND l.create_time = ?)
    -- 根据当前页主键继续追加，最多 100 组
;
```

明细 SQL 不做外层排序；应用查询完毕后，按第一步得到的主键顺序恢复列表顺序。

必须同时使用 `id` 和 `create_time`，因为日志表的主键是 `(id, create_time)`。这样既能准确定位记录，也能利用完整复合主键进行回查。

## 四、优化内容与原因

|优化内容|为什么这样做|
|---|---|
|先分页查询复合主键|缩小主分页查询的投影范围，让请求、响应等大文本不参与主分页查询的返回和排序处理，降低排序阶段的数据宽度。|
|再按主键批量查询明细|只对当前页记录读取完整字段和最新处理记录，避免对每条记录单独查询，也避免对大批候选记录直接返回正文。|
|应用按主键恢复顺序|明细回查不需要再次对完整正文做外层排序，同时保留第一步确定的告警优先及日志倒序。|
|未筛选处理状态时，主键分页不关联处理历史|处理历史不影响“全部处理状态”下的页面成员和排序；只在需要按处理状态筛选时提前关联，减少不必要的关联和子查询。|
|保留原来的筛选和排序规则|调用状态、处理状态、时间、接口等条件仍在分页前生效；当前启用且告警的接口仍优先展示。|
|总数查询保持原逻辑|保持页面总数口径一致，本次优化集中解决列表查询的排序压力。|

|测试项|结果|平台显示耗时|
|---|---|---|
|优化前列表 SQL|报 MySQL 1038|无成功耗时|
|优化后：主键分页|成功返回 10 条|0.561 秒|
|优化后：明细回查|成功返回 10 条|0.008 秒|
|总数查询|返回 79,830 条|0.584 秒|

按本次独立测试的耗时相加，优化后列表两步约 **0.569 秒**；加上总数查询约 **1.153 秒**。这只是数据库平台上的参考值，实际页面还包含多次数据库往返、应用处理和网络耗时。

由于优化前 SQL 报错，没有成功耗时，**无法计算准确的提速倍数**。现有结果能说明：在这一次生产数据和筛选条件下，优化后的两步列表查询均成功执行。

### 执行计划观察

- 主键分页使用 `idx_start_at`，`type = range`，`rows = 217440` 是优化器预估值，**不等于实际扫描行数**。
- 主键分页仍显示 `Using temporary; Using filesort`。跨表告警优先排序仍需额外排序，但这次查询成功返回；不能仅凭 `Using filesort` 判断存在性能问题。
- 明细回查使用复合主键 `PRIMARY`，`rows = 10` 为预估值，符合按当前页 10 组主键回查的预期。

## 六、影响与后续验证

本次未修改生产数据库索引或参数，也未部署。代码仍沿用非事务只读查询：如果主键筛选完成后，其他用户恰好更新处理状态，回查时展示的状态可能与筛选时暂时不一致。

部署后建议重点验证：

1. 重新查询 **11 月 3 日、全部状态、第一页**，确认页面不再报 1038，并记录页面实际响应时间。
2. 检查调用状态、处理状态的组合筛选，以及告警优先顺序和翻页结果。
3. 如果页面仍慢，分别观察总数查询、主键查询和明细回查的耗时及执行计划，再决定是否需要继续调整索引或查询方案。
