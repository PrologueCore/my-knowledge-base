# 批量导出导致数据库连接池耗尽

## 场景与现象

Java 报表导出先查询主记录，再查询每条主记录对应的明细。主记录达到数千条时，导出期间出现获取数据库连接超时，连接池活跃连接达到上限。连接池由多个业务共享，其他请求也可能因等待连接而变慢或超时；具体影响范围应以监控和日志为准。

以下示例经过泛化，数字仅用于说明量级和设计方法，不作为通用容量建议。

## 问题模式

```java
for (Record record : records) {
    futures.add(CompletableFuture.runAsync(() -> {
        List<Detail> details = queryDetails(record.getId());
        result.put(record.getId(), details);
    }));
}
CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
```

每条主记录对应一个任务和一次明细查询，属于 N+1 查询。未指定执行器时，异步任务使用默认执行器；任务数量不等于同时执行线程数，但大量阻塞式数据库查询仍会在并发、连接持有时间和其他业务负载共同作用下耗尽共享连接池。

## 改造方法

1. 收集主记录 ID，以有界批次执行参数化批量查询。例如 4000 个 ID、每批 500 个，理论上约 8 次明细查询，实际次数以有效 ID 数和实现为准。
2. 使用单实例内共享的专用线程池，显式设置线程数、有界队列和拒绝策略。一个示例是 4 个工作线程、队列容量 100，具体值需要结合连接池预算和负载测试确定。
3. 分波提交：每个请求每波最多提交 4 个批次，等本波完成再提交下一波。5000 条数据仍会形成 10 批，但不会由单个请求一次性提交全部 10 批。
4. 合并结果时按主记录关联并恢复既有导出顺序，补齐原先由主记录填充的展示字段；核对新旧 SQL 的字段、关联、过滤条件和排序语义，防止性能优化造成数据缺失。
5. 批次失败时向上报告，避免将部分明细当作完整结果；提交被拒绝时处理已提交任务并报告失败。取消 Future 不保证已经执行的数据库查询会立即停止。

## 边界和取舍

- 分波限制的是每个请求同时提交的批次数，不是全系统的排队上限；多个请求共享同一有界队列，饱和时 `AbortPolicy` 仍会拒绝任务。需明确向调用方返回失败或设计受控重试，不能静默丢弃。
- 共享线程池的并发上限通常只在单个 JVM 内生效；多实例部署时，应结合实例数评估数据库总并发。
- `CallerRunsPolicy` 可能让请求线程执行查询，增加数据库并发；直接扩大连接池也可能把压力转移到数据库。
- 单批 ID 数不是明细行数上限，批量查询可能产生大量结果；应监控内存、SQL 耗时，并按需要评估分页或流式导出。
- 分批执行期间数据可能变化；如需跨批一致快照，须结合数据库隔离级别和业务要求单独设计。

## 验证方式

- 对比改造前后导出行数、关键字段、顺序和关联结果，覆盖空数据、边界批次、多批次及并发请求。
- 注入批次查询失败与线程池饱和场景，确认调用方能感知失败，检查没有误报成功的残缺文件。
- 观察连接池活跃数、等待时间、数据库查询次数和耗时，并在多实例场景核算总并发。
